# The flow

This page maps the repository: which files you edit, what each `make` target runs, and how the pieces connect, from C source to a Tiny Tapeout GDS.

## The repository

| Path | What | Yours? |
|---|---|---|
| `src/core/` | the core: register file, ALU, immediate generator, control FSM, datapath, `rv32u_ctrl.svh` | **yes** |
| `src/io/` | the program loader and the I/O registers (D2-D5) | **yes** |
| `src/rv32u_pkg.sv` | encodings, selectors, the memory map | no |
| `src/mem/` | the memory subsystem and the three RAM options (D1) | no (select one) |
| `src/rv32u_soc.sv`, `src/tt_um_sharc_rv32u.sv` | the system and the Tiny Tapeout top level | the pin mapping (D5) |
| `src/config.json`, `src/config/`, `src/pdn_cfg.tcl` | LibreLane hardening configuration | generated by `select-memory.py` |
| `info.yaml` | the Tiny Tapeout project description: top module, sources, tiles, pinout | the pinout (D5) |
| `ip/` | the IHP SRAM models (a sparse submodule) and their FuseSoC core | no |
| `sw/` | `crt0.S`, the linker script, the ISA tests (`isa/*.S`), the C programs (`c/*.c`), the legalizer | add your programs |
| `verif/` | the reference model, the lockstep harness, the ISA and C tests | add your unit tests |
| `test/` | the Tiny Tapeout cocotb test (RTL and gate level) | extend it (M4) |
| `DESIGN.md` | your design decisions | **yes** |
| `docs/` | this site | no |

## From C to a passing test

```
sw/c/fib.c --gcc -S--> fib.s --legalize.py--> fib.legal.s --gcc + crt0.S, link.ld--> fib.elf
    --check_subset.py (only the 14 instructions?)--> --objcopy, bin2hex--> sw/build/c/fib.hex
```

1. `make -C sw` compiles each program with `-march=rv32i -mabi=ilp32 -O0 -nostdlib`. `legalize.py` rewrites the few RV32I instructions that GCC emits outside the subset (such as `bne` and `slli`) into ones inside it. `check_subset.py` then fails the build if any other instruction remains ([chapter 8](../spec/08-software-flow.md)).
2. The test (`verif/test_isa.py` or `verif/test_c.py`) loads the `.hex` into the RAM through the simulator, releases reset, and runs your core and the reference model (`verif/model/rv32u_iss.py`) in lockstep. Every retired instruction must match ([chapter 9](../spec/09-verification.md)).
3. At the halt, the `expect:` results in the program's header are checked.

## The `make` targets

| Target | Runs |
|---|---|
| `make setup` | `uv sync`, and the sparse SRAM-model checkout |
| `make check-env` | `scripts/check-env.sh` |
| `make sw` | `make -C sw`: every ISA test and C program |
| `make lint` | FuseSoC target `lint` of `sharc:rv32u:soc`: Verilator `-Wall` |
| `make isa`, `make c` | FuseSoC targets `isa`/`c` (or `isa_icarus`/`c_icarus`) of `sharc:rv32u:tb` |
| `make tt-test` | `make -C test`: the Tiny Tapeout smoke test |
| `make test` | lint, isa, c and tt-test |
| `make model-test` | pytest on the reference model |
| `make design-check` | `scripts/check_design.py`: is every `DESIGN.md` field filled in? |
| `make memory OPT=...` | `scripts/select-memory.py` (D1) |
| `make site` | `quarto render docs` |

Options: `SIM=icarus` simulates with Icarus Verilog; `WAVES=1` dumps a waveform (Icarus); `COCOTB_TEST_FILTER=<name>` runs one test.

## FuseSoC

[FuseSoC](https://fusesoc.readthedocs.io) describes each part of the design as a *core* (a `.core` file) with its files and its build targets. `make` calls it with explicit core roots:

```bash
uv run fusesoc --cores-root src --cores-root ip --cores-root verif \
    run --no-export --target=isa sharc:rv32u:tb
```

| Core | File | Contains |
|---|---|---|
| `sharc:rv32u:pkg` | `src/rv32u_pkg.core` | the package (and your `rv32u_ctrl.svh`) |
| `sharc:rv32u:core` | `src/core/rv32u_core.core` | your core |
| `sharc:rv32u:io` | `src/io/rv32u_io.core` | your loader and I/O |
| `sharc:rv32u:soc` | `src/rv32u.core` | the system, the RAM option, the `lint` target |
| `sharc:ip:ihp_sram` | `ip/ihp_sram.core` | the SRAM behavioural models |
| `sharc:rv32u:tb` | `verif/rv32u_tb.core` | the cocotb targets: `isa`, `c`, and your `unit_*` targets |

Builds go to `build/sharc_rv32u_tb_0.1.0/<target>/`, with the simulator's log, `results.xml` and any waveform.

## Tiny Tapeout

The Tiny Tapeout flow runs in GitHub Actions on every push ([chapter 10](../spec/10-tiny-tapeout.md)):

| Workflow | Jobs |
|---|---|
| `.github/workflows/gds.yaml` | `gds` (LibreLane hardening with the SRAM power plugin), `precheck`, `gl_test` (the `test/` cocotb test on the netlist), `viewer` (rebuilds the site with the new layout) |
| `.github/workflows/docs.yaml` | the Tiny Tapeout datasheet from `docs/info.md` |
| `.github/workflows/site.yml` | this site, published to the repo's GitHub Pages, with the latest layout under `viewer/` |
| `.github/workflows/verify.yaml` | lint, the ISA and C tests, and the `DESIGN.md` check |

`info.yaml` and `src/config.json` must agree with the RAM option. `scripts/select-memory.py` keeps them consistent; do not edit the generated parts by hand.
